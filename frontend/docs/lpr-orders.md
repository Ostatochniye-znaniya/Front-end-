# Приказы ЛПР: форма, API и жизненный цикл

Страница `/csh/lpr/order` работает с реальным API. Моков и переключателей режима нет.
Приказы и черновики хранятся в `orders`, общий SegmentedToggle переключает фильтр `status`.
Обе модалки используют общий Modal и секцию MODAL в globals.css.

## Где находится логика

| Этап | Файл во frontend | Запрос |
| --- | --- | --- |
| Открытие страницы / переключение вкладки / обновление | `app/lpr/order/page.tsx`, эффект загрузки | GET /csh/api/getOrdersEssentials?status=issued либо draft |
| Открытие формы, справочник реальных Semester.Id | `components/orders/CreateOrderModal.tsx` | GET /csh/api/Semester/GetSemesters |
| Проверка полей и дат, Tab/Shift+Tab по кругу | `services/orderForm.ts`, CreateOrderModal | Без сети |
| «Сформировать приказ» / «Сформировать черновик» | CreateOrderModal → `services/orders.ts:createOrder` | POST /csh/api/createOrder |
| Открытие карточки документа | `components/orders/OrderDetailsModal.tsx` | GET /csh/api/getOrderDetails/{id} и отдельный GET /csh/api/getOrder/{id} |
| «Подписать» в черновике | OrderDetailsModal → `services/orders.ts:signOrder` | POST /csh/api/signOrder/{id} |
| Скачивание | OrderDetailsModal:download | Уже загруженный PDF Blob |

Все fetch-запросы, DTO, проверка JSON и разбор ошибок — в `services/orders.ts`.
Парные даты общего периода, трёх этапов и анкетирования объединены в одну строку процесса:
справа две ячейки с полями «Начало» и «Конец» и подписями на рамке.
Группировка задана в `services/orderForm.ts:ORDER_FORM_DATE_RANGES`; названия полей API
и проверки не меняются. Tab идёт сначала к концу периода, затем к следующему процессу.
После создания список обновляется и выбирается соответствующая вкладка.
После подписания карточка показывает присвоенный номер, список переходит к приказам,
старый PDF отбрасывается и загружается новый. Во время подписания скачивание заблокировано.
У реквизитов и PDF независимые загрузки и ошибки с повторной попыткой.
Поиск по официальному номеру выполняется локально в выбранной вкладке;
без поисковой строки видны и черновики без номера.

## Запрос создания

`number` фронт больше не отправляет. Передаются:

| Поля | Смысл |
| --- | --- |
| status | draft / issued; все остальные обязательные реквизиты проверяются для обоих |
| orderDate, semesterId | Дата документа и настоящий Semester.Id из справочника |
| testingStartDate, testingEndDate | Общий период всех мероприятий, пункт 1 приказа |
| preparationStartDate, preparationEndDate | Начало и окончание 1 этапа |
| testingStageStartDate, testingStageEndDate | Отдельные границы 2 этапа — фактического тестирования |
| resultsProcessingStartDate, inspectionSummaryDeadline | Начало и окончание 3 этапа; окончание одновременно является сроком сводного отчёта, как в действующем шаблоне |
| onlineSeminarDate | Дата обучающего онлайн-семинара для сотрудников |
| surveyStartDate, surveyEndDate, surveySummaryDeadline | Прежние реквизиты анкетирования: по договорённости продолжают передаваться, хотя PDF их не использует |
| requiresPaperReports | Чекбокс «Сдавать бумажные отчёты» |
| paperReportDeadline | Обязателен при true; при false поле скрыто и отправляется null |
| electronicReportDeadline | Дедлайн электронных отчётов |
| educationControlDepartmentHead, educationalMethodicalCenterHead | ФИО ответственных |

Даты — календарные строки YYYY-MM-DD для DateOnly, без пересчёта часового пояса.
Вместо прежних academicYear/checkedSemester передаётся только semesterId.
Учебный год и подпись семестра для показа вычисляются из записи справочника.

Все даты мероприятий и отчётов, включая анкетирование, должны быть внутри общего периода
(обе границы включительны). Дата самого приказа этим правилом не ограничивается.
Этапы идут последовательно: подготовка → тестирование → обработка; допускается общая
граничная дата соседних этапов. Анкетирование заканчивается не раньше начала,
его сводный отчёт — не раньше окончания. Календарь дат имеет min/max, но решающая
проверка выполняется при отправке и повторяется на беке в OrderDates.Validate.
Скрытый бумажный дедлайн не блокирует отправку и не попадает в PDF.

## Статусы и номер

- draft сохраняется с number: null. В PDF есть отметка «ЧЕРНОВИК» и «без номера».
- issued получает номер n-ОД на сервере, как при прямом создании, так и при подписании.
- «Подписать» означает выпуск документа, не электронную криптографическую подпись.
- Повторное подписание issued возвращает тот же документ и не выдаёт другой номер.
- Счётчик общий, без ежегодного сброса. Продолжается максимальный старый числовой номер:
  например, после 233 следующий — 234-ОД. Старые официальные номера не переименовываются.
- Частичное сохранение и редактирование уже созданного черновика здесь не реализованы.

Бек сериализует выдачу номера через единственную строку order_number_sequence FOR UPDATE,
сохраняет счётчик и документ одной транзакцией; номер защищён уникальным индексом.
Технический creation_token защищает создание от повторного COMMIT при восстановлении соединения.
PDF сначала формируется и сохраняется, затем фиксируются реквизиты.
При подписании новый PDF содержит номер, отметка черновика исчезает.
Старый объект очищается только после подтверждения, что БД больше на него не ссылается.

## Ответы и старые документы

Список: id, number (string | null), name, status, orderDate, общие даты,
semester: { id, semesterYear, semesterPart }.
Карточка дополнительно возвращает все этапы, семинар, анкетирование, сроки отчётов,
флаг бумаги, размер PDF, CreatedAt и автора (ID/имя). Внутренний ключ S3 наружу не отдаётся.

Для старых документов новые/отсутствовавшие даты допускают null в БД и ответе карточки:
вместо выдуманного значения показывается «Не указано». Для нового документа эти даты обязательны.
Старый неполный черновик нельзя подписать в обход проверки: сначала нужны корректные реквизиты;
редактирование такого документа потребует отдельной доработки либо создания нового черновика.
Дата, номер и уже сохранённый PDF старого выпущенного приказа при миграции не пересоздаются.

## Бек и запуск

В репозитории KnowledgeApp:
OrderController — маршруты; OrderService — создание/подписание и работа с хранилищем;
OrderDates — проверки; OrderRepository — транзакции, блокировки, счётчик, чтение/запись;
OrderPdfGenerator — основной текст и приложения.
Полная схема перехода и предосторожности описаны в `KnowledgeApp/docs/lpr-update.md`.

Фронт требует существующий Nginx, проксирующий /csh/api/ на API без этого префикса.
Один next dev этот прокси не создаёт. Нужны обновлённая схема БД и работающее S3/MinIO.
Фронт и бек следует обновлять вместе; пересборка Docker сама по себе не обновляет данные volume.
